# AWS KMS – 1. Basics, key types and access control

Short notes. Each point is a fact you can be asked about.

## A. What it is
- **AWS Key Management Service (KMS)** creates and controls **cryptographic keys** and uses them to encrypt/decrypt/sign/MAC. Keys are protected in **FIPS 140-3 validated HSMs**; the plaintext KMS key **never leaves KMS** unencrypted.
- It is **Regional**: a KMS key lives in one Region (except multi-Region keys, which are linked copies).
- It integrates with **100+ AWS services** (S3, EBS, RDS, Redshift, DynamoDB, Glue, EMR, Kinesis, Firehose, MSK, Lambda, Secrets Manager, CloudWatch Logs, CloudTrail…) and is logged in **CloudTrail**.
- Pick it when: you need **central key control, audit, rotation, cross-account sharing** for encryption at rest, or a service demands a **customer managed key**.
- Alternatives: **CloudHSM** (dedicated single-tenant HSM you control fully), **AWS Encryption SDK** (client-side library that uses KMS), **Secrets Manager/Parameter Store** (store secrets, not keys), **S3 SSE-S3** (no key control, free).
- DEA-C01: **4.3 Apply data encryption and masking** (KMS keys, key policies, client-side vs server-side, cross-Region encryption, Glue/Redshift/S3 encryption).

## B. Key concepts
- **KMS key** (formerly "customer master key", CMK): a logical key (ID, ARN, metadata, key material).
- **Key material**: the actual cryptographic secret. A KMS key can have several versions after rotation.
- **Data key**: a symmetric key generated by KMS (`GenerateDataKey`) to encrypt data **outside** KMS; the KMS key encrypts ("wraps") the data key. This is **envelope encryption** (file 2).
- **Key ID** (UUID), **key ARN**, **alias** (`alias/name`, pointer to a key), **alias ARN**. Use the **key ARN** for cross-account/cross-Region references.
- **Alias rules**: must start with `alias/`; **not** `alias/aws/` (reserved for AWS managed keys); unique per Region/account; **up to 50 aliases per key**; an alias can point to only **one key**; changing the alias target is the common **manual rotation** trick.
- **Encryption context**: optional key-value pairs of **non-secret** data bound to the ciphertext as **additional authenticated data (AAD)**. Decrypt must supply the **same context**. Appears in **CloudTrail**; usable in policy conditions (`kms:EncryptionContext:key`).
- **Grant**: temporary, programmatic permission to use a key (used heavily by AWS services such as EBS, RDS, Redshift). Retire/revoke when done. **Up to 50,000 grants per key.**
- **Key state**: Enabled, Disabled, PendingDeletion, PendingImport, Unavailable (custom key store disconnected), Creating, Updating.
- **Key spec / usage**: what the key is for.
  | Type | Key usage | Notes |
  |---|---|---|
  | **Symmetric encryption** (AES-256-GCM, `SYMMETRIC_DEFAULT`) | Encrypt/decrypt, GenerateDataKey | Default; used by almost all AWS services; supports automatic rotation |
  | **Asymmetric RSA** (2048/3072/4096) | Encrypt/decrypt **or** sign/verify | Public key downloadable; no auto rotation |
  | **Asymmetric ECC** (NIST P-256/384/521, secp256k1) | Sign/verify (or key agreement for some) | Smaller signatures |
  | **SM2** (China Regions) | Sign/verify, encrypt/decrypt | China only |
  | **HMAC** (224–512) | GenerateMac / VerifyMac | Tokens, API signing |
  | **ML-DSA (post-quantum)** | Sign/verify | Newer **(verify)** |
- **Key spec and key usage cannot be changed** after creation.
- **Asymmetric KMS keys can't be used for most AWS service encryption** (services need symmetric keys), except specific cases (for example signing in Private CA, JWT).

## C. Three kinds of keys
| Kind | Who owns/manages | Visible in your account? | Cost | Control |
|---|---|---|---|---|
| **AWS owned key** | AWS service (shared across accounts) | **No** | Free | None; no CloudTrail of key use |
| **AWS managed key** (`aws/s3`, `aws/rds`, `aws/glue`…) | AWS creates in your account for a service | Yes | **No monthly fee** (requests billed) | Key policy fixed; **rotates every year** (cannot disable); cannot be shared cross-account |
| **Customer managed key (CMK)** | You | Yes | **$1/month** + requests | Full: policy, rotation, grants, disable, delete, cross-account, multi-Region |
- **AWS managed keys** are named `aws/<service>`; you can view them and audit use in CloudTrail but **cannot edit the policy or delete them**. They allow use **only via that service** (`kms:ViaService`).
- **Use a customer managed key** when you need: cross-account access, custom policy, audit separation, rotation control, ability to **disable/delete (crypto-shred)**, or a compliance mandate.
- **Cross-account use requires a customer managed key** (AWS managed keys cannot be shared).
- Service defaults: S3 SSE-S3 (AWS owned), SSE-KMS (AWS managed `aws/s3` unless you choose a CMK); Redshift/RDS/EBS ask you to pick `aws/<service>` or a CMK.

## D. Key origin
- **AWS_KMS** (default): KMS generates and holds the material.
- **EXTERNAL**: you **import your own key material** (BYOK). You manage expiry and can delete the material; KMS cannot recover it; **no automatic rotation** (on-demand rotation possible after importing new material). Material must be wrapped with a KMS-provided public key and import token (valid ~24 hours).
- **AWS_CLOUDHSM**: key material in your **CloudHSM cluster** (custom key store).
- **EXTERNAL_KEY_STORE (XKS)**: key material stays in an **external key manager** outside AWS; KMS proxies the crypto operations. Highest control, higher latency and availability risk.

## E. Who can use a key: three mechanisms
1. **Key policy** (required, exactly one per key, resource-based, Regional).
2. **IAM policies** (work **only if the key policy allows IAM policies**).
3. **Grants** (programmatic, delegated, revocable).
- **No one has permission by default**, not even the account root, unless a policy/grant allows it.
- **Default key policy** (console): one statement lets the account **root principal** do `kms:*` on `*`. This "root" statement **enables IAM policies** to control the key. Without it, IAM policies have no effect.
- A key policy that lists **specific principals** (and no root statement) means only they can use/manage it. If you lock yourself out, you must contact AWS Support (the account root can be re-added only with a way to change the policy).
- **Key administrators vs key users** (console key policy template):
  - Administrators: create, describe, enable/disable, put key policy, schedule deletion, tag, alias, rotate; **no use** in crypto ops.
  - Users: `Encrypt, Decrypt, ReEncrypt*, GenerateDataKey*, DescribeKey`.
  - Plus a statement for **service use with grants**: `CreateGrant, ListGrants, RevokeGrant` with `kms:GrantIsForAWSResource = true`.
- **Key policy size** limit: **32 KB**. **IAM policies and key policies are evaluated together**: explicit deny anywhere wins.
- An IAM policy can **deny** a KMS action even if the key policy does not mention the principal.
- **Cross-account use**: key policy in the key's account allows the **other account** (or specific principals); the **other account's IAM policy** must also allow the KMS actions on the key ARN. Both are required. (A grant also works across accounts for AWS services.)
- **Condition keys** to know:
  - `kms:ViaService` – only when the request comes through a named service (for example `s3.us-east-1.amazonaws.com`).
  - `kms:CallerAccount` – restrict to a specific account.
  - `kms:EncryptionContext:<key>` and `kms:EncryptionContextKeys` – bind use to a context.
  - `kms:GrantIsForAWSResource`, `kms:GrantOperations`, `kms:GranteePrincipal`.
  - `kms:ResourceAliases`, `kms:KeyUsage`, `kms:KeySpec`, `kms:KeyOrigin`, `kms:MultiRegion`, `kms:ReplicaRegion`, `kms:RotationPeriodInDays`.
  - `aws:PrincipalOrgID`, `aws:SourceArn`, `aws:SourceAccount` (confused deputy), `aws:SourceVpce`.
- **KMS actions** you will see: `kms:Encrypt`, `Decrypt`, `ReEncryptFrom/To`, `GenerateDataKey`, `GenerateDataKeyWithoutPlaintext`, `GenerateDataKeyPair*`, `GenerateRandom`, `DescribeKey`, `CreateGrant`, `ScheduleKeyDeletion`, `CancelKeyDeletion`, `EnableKeyRotation`, `PutKeyPolicy`, `Sign`, `Verify`, `GenerateMac`, `ReplicateKey`.
- **`kms:DescribeKey` and `kms:ListKeys` etc.** need Resource `*` for some (listing); `Decrypt` of ciphertext infers the key from the ciphertext blob.

## F. Typical key policy patterns
- **Admin/user separation**: Admin role manages, app role uses; neither has the other's rights.
- **Service-scoped use**: Allow `Encrypt/Decrypt/GenerateDataKey*` with `kms:ViaService = s3.<region>.amazonaws.com` and `kms:CallerAccount = <acct>` so the key works only through S3 for your account.
- **Data perimeter**: Deny when `aws:PrincipalOrgID` ≠ your org and `aws:PrincipalIsAWSService` false (also RCP for KMS).
- **Cross-account share**: Allow `Principal: arn:aws:iam::<other>:root` with the crypto actions; the other account then delegates through IAM.
- **Prevent deletion**: Deny `kms:ScheduleKeyDeletion` and `kms:DisableKey` to all but a break-glass role.
- **Crypto-shred**: remove access or delete the key to make all data unreadable.
- **Third-party log delivery** (CloudTrail, CloudWatch Logs, Firehose, Config, SNS, SQS, S3 events): the **service principal** must be in the key policy (for example `cloudtrail.amazonaws.com`, `logs.<region>.amazonaws.com`, `delivery.logs.amazonaws.com`) with `aws:SourceArn` / encryption context conditions.
- **Redshift/EMR/Glue**: the **service role** needs key permissions (identity policy) and the key policy must allow that role or enable IAM policies.

## G. Key lifecycle
- **Create** → **Enable/Disable** (disabled keys cannot be used; reversible) → **Schedule deletion** (**waiting period 7–30 days**, default **30**) → **Delete** (irreversible).
- During **PendingDeletion** the key cannot be used and not rotated; **CancelKeyDeletion** returns it to **Disabled** (then enable).
- Prefer **disable** first to test impact (CloudTrail will show failed uses); then schedule deletion.
- A CloudWatch alarm on `kms:Decrypt` failures / CloudTrail `KMSInvalidStateException` during the waiting period reveals who still needs the key.
- **Deleting a key makes all data encrypted under it unrecoverable** (including backups and snapshots).
- **Imported key material** can be deleted immediately (`DeleteImportedKeyMaterial`), making the key unusable until re-imported.
- **Multi-Region primary** with replicas: can't schedule deletion of the primary until replicas are deleted (or promote another).
- **Replica keys** have their own policy and state.

## H. Cost (basics)
- **$1 per customer managed key per month**, prorated hourly (each multi-Region primary/replica counts).
- **Rotated key material**: first and second rotation each add **$1/month**; no more after that.
- **Requests**: about **$0.03 per 10,000** symmetric requests; **$0.15 per 10,000** for asymmetric; **20,000 free requests/month**; HSM/XKS keys also pay HSM costs.
- **AWS managed keys**: no monthly fee; API requests billed (after free tier).
- Frequent KMS calls (S3 SSE-KMS at scale) can be a **major cost** → use **S3 Bucket Keys** (file 3).

## J. Scenarios: "If X → Y, because Z"
- If compliance needs you to control and audit the encryption key → **customer managed key with a custom key policy**, because AWS managed keys cannot be edited or shared.
- If account B must decrypt data encrypted by account A's key → **key policy allows account B + B's IAM policy allows `kms:Decrypt` on the key ARN**, because both policies must allow.
- If IAM policies seem to have no effect on a key → **the key policy lacks the root "enable IAM policies" statement**, because KMS authorizes through the key policy first.
- If you need to restrict a key to only be used by S3 in your account → **`kms:ViaService` + `kms:CallerAccount` conditions**, because the key cannot then be used directly or by other services.
- If you must prove data is gone → **schedule key deletion (7–30 days) after disabling**, because deleting the key makes ciphertext unrecoverable.
- If someone accidentally scheduled deletion → **`CancelKeyDeletion` within the waiting period and re-enable**, because the key is only gone after the period ends.
- If you need your own key material (BYOK) → **EXTERNAL origin import**, because KMS then uses your material; plan manual rotation and key backup.
- If regulations require keys outside AWS → **External Key Store (XKS)**, because the key material never enters AWS.
- If you need single-tenant HSM control → **CloudHSM custom key store**, because you own the HSM cluster.
- If a service log delivery to an encrypted bucket/topic fails → **add the service principal (with SourceArn condition) to the key policy**, because the service must call `GenerateDataKey/Decrypt`.
- If an app signs documents → **asymmetric ECC/RSA sign/verify key**, because symmetric keys cannot sign.
