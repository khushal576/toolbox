# SQL Practice — tool-local notes

> **Start here:** repo rules `../CLAUDE.md` · where things live: `./KNOWLEDGE_MAP.md`. Content (datasets + questions) lives OUTSIDE this repo in `../../learn-sql/practice/`, mounted read-only at `/practice` in `rt-data` (`TOOLBOX_PRACTICE_DIR`, compose).

## What it is
LeetCode-style SQL practice. Pick a question → read it → open **Schema** (panel above the page) → write a query in the editor → **Run**.
**Check** runs your query and the reference, compares both result sets with DataDiff (`provision.check`): columns must match by name AND order; numbers are rounded to 2 decimals; text is exact (DataDiff calls 'y'/'Y' EQUIVALENT — we treat anything but MATCH as a difference). Unordered questions match rows by content (so you see "missing" / "unexpected" rows); `compare: {order_matters: true}` first compares the ROWS by content (extra / missing rows are reported, positional cell diffs are suppressed because extra rows shift every later position); only when the rows are right does it compare by position, which yields the "right rows, wrong order — add a tie-breaker" hint.
**Progress** is in Toolbox's own Postgres, schema `sql_practice` (so Toolbox backups cover it). Status: new → attempted → solved (✓) | revealed (gave up after 3 wrong Checks; counts for moving on, not for ✓, to be revisited). A syntax error is not an attempt.
**Order:** `questions/_path.yaml` lists the topics in order, then by id; a question is locked until the one before it is solved/revealed (the page's "Keep order" box can be unticked; it is not enforced by the server). **The solution, `trap`, `followup` and `alternatives` fields of a question file reach the browser only once it is completed.**
Question YAML extras: `trap`, `followup`, `alternatives` (shown after completion), `compare: {order_matters, decimals}`.
**Plan questions** (`check: {type: plan, must_use: [...], must_not_use: [...]}`, for performance reasoning): Check also runs `EXPLAIN (FORMAT JSON)` of the learner's query (`provision.explain_plan`; plan only, NOT executed, same restricted role / read-only rolled-back transaction / search_path) and matches the plan tree (all `Plans`, SubPlans included). An entry matches a node by `Node Type` (case-insensitive) or `X on relation`; `|` separates alternatives (any one satisfies the entry), all `must_use` entries must be satisfied, no `must_not_use` entry may match; `Anti Join` / `Semi Join` match any join node whose Join Type contains Anti / Semi. Correct = result matches the reference AND plan rules hold. The verdict shows the plan text (pass and fail) plus which rule failed; the page gets only a general `check.note` (derived, or the optional `check.note` in YAML), never the node names. The reference SQL is not subject to the rules. An EXPLAIN error (syntax) is not an attempt. **Explain** button + `POST /explain {dataset, sql}` -> `{nodes, node_types, text}` work for any question. Plans depend on planner stats: `_load_dataset` ends with `VACUUM ANALYZE` (stats + visibility map, so Index Only Scan is possible); keep plan rules to robust facts (index vs seq scan), not costs.
**Mock interviews** (🎯 button in the header): a SET (in `questions/_mocks*.yaml` — every file matching is read, so authors can own one file each; set ids must be unique across files: `sets: [{id, title, domain, minutes, intro, questions: [3 ids]}]`) chains 3 ordinary question files (`questions/mock-interviews/mk-NNN-*.yaml`, topic `mock-interviews`) under a SERVER-SIDE clock. Mock questions are NOT in `/questions`, the path, locks, counts or `next_id` (`ordered_questions` drops topic `mock-interviews` and every id used in a set); `get_question`/`/check`/`/validate` still see them. Runs live in `sql_practice.mock_runs` (id, set_id, started_at, ends_at, finished_at, results jsonb; created lazily next to `progress`). Rules: `POST /mocks/{set}/start` starts a run (or returns the running one); starting FORGETS the progress of the set's 3 questions (a run is a clean attempt); a run auto-finishes at `ends_at` lazily whenever anything reads (`_expire_runs`) and `POST /mocks/{set}/finish` ends it early; results (status/attempts per question) are snapshotted at finish; score = questions solved. `POST /check` on a mock question is refused unless the set has a running run; there is no reveal (403); solution/trap/follow-up show only for solved questions or, after the run is finished, for all 3. Endpoints: `GET /mocks` (sets + status not_started|in_progress|finished, remaining_seconds, best/last score), `GET /mocks/{set}` (409 until a first run exists; set, run, the 3 `get_question()` outputs), `GET /mocks/questions` + `POST /mocks/runs/{id}/discard` (harness: `tools/check_traps.py` starts the set, checks, resets, discards its test run; it skips sets that are running). `/validate` also returns `mocks` (per set: 3 existing distinct ids, unique set id, minutes > 0, title/intro present; orphan mock questions). UI: the countdown is computed from the server's `remaining_seconds` at fetch time (no local-clock trust); the mock screen reuses the normal question pane (`openQuestion`, `checkAnswer`; `state.mock` switches the sidebar off and the tab bar on). Authoring rules: `learn-sql/practice/AUTHORING.md`, section MOCK INTERVIEW SETS.
**Revisit queue** (🔁 Review (n) + 📉 Weak topics buttons). A question needs revisiting when the learner needed help: it was `revealed`, or solved after >= 3 failed Checks ("hard-won"). Columns on `sql_practice.progress` (added lazily with `ADD COLUMN IF NOT EXISTS`): `revisit_stage` (the stage awaited, 0 = none), `revisit_due`, `revisit_done_at`. Rules (pure functions `revisit_due_at / revisit_is_open / revisit_plan` in provision.py, injectable `now`, unit-tested in `tests/unit/test_sql_practice_revisit.py`): stage 1 is due 3 days after the reveal / hard-won Check; a correct Check while the revisit is OPEN (`revisit_due <= now`) moves to stage 2 due 10 days after that Check; a correct Check on an open stage 2 ends the cycle (`revisit_due` NULL, `revisit_done_at` set = mastered, never due again); a wrong Check never changes anything (stays due, attempts count); revealed + correct Check = `solved` (earns the check mark). While open, `get_question` hides solution/trap/follow-up (and `/check` returns no `solution` until the correct Check closes the revisit), and returns `revisit: {stage, open, due_at}`; the sidebar shows 🔁 (list items carry `revisit_due`, summary `revisits_due`), the pane a banner. Locking is unchanged (revealed still unlocks the next question). Mock questions are excluded everywhere. Rows revealed before this feature have no schedule (not backfilled). Endpoints: `GET /revisits` -> `{due, upcoming: [{id,title,topic,due_at,stage}], counts: {due, upcoming, mastered}}`; `GET /weak-topics` -> `{topics: [{topic,total,solved,revealed,attempted,hard_won,failed_checks,attempts,started,accuracy}]}` sorted weakest first (lowest solved share among started questions, then most failed Checks per started question; accuracy = solved questions / total Check attempts). The Practice action in the Weak topics table sets the topic filter of the sidebar.

## Decisions (owner, 2026-11-14)
- **Own database `practice`** on Toolbox's bundled Postgres, no new container. One SCHEMA per dataset.
- **Learner SQL never runs as the `toolbox` login** (that database holds the Vault). It runs as `practice_user`: CONNECT on the toolbox DB is revoked from PUBLIC, SELECT only on the dataset schemas, read-only transaction, always rolled back, 10 s timeout, 500-row cap, one statement per request (`prepare=True`). Setup alone uses the `toolbox` login (a superuser on the bundled Postgres; an external Postgres needs a role that may CREATE ROLE/DATABASE).
- **The editor is a COPY of SQL Studio's** (`ui/vendor/cm-bundle.js` + the schema→autocomplete function) so SQL Studio can change freely. No connection panel: the editor is already connected; autocomplete comes from `GET datasets/<ds>/schema.json`.
- **Schema preview = a generated page, in Schema Map's look**: circles sized by row count, FK arrows, plus a LEFT column list (types, PK, FK, NOT NULL; click a table in either place to highlight its neighbours). Built from the live practice database by `provision.schema_page()` + `ui/schema_template.html` and served at `datasets/<ds>/schema.html`, so it never drifts and needs no manual export. A hand-saved `learn-sql/practice/datasets/<name>/schema.html` (e.g. a real Schema Map export) overrides it if present. The panel is a fixed OVERLAY above the page (owner: opening it must not move or re-render the question/editor); Esc closes it.
- Questions are YAML files, `questions/<topic>/<id>.yaml`; `solution_sql` is never sent to the browser. `GET /validate` runs every reference SQL (must run, return rows, be deterministic).

## Files
- `provision.py` — create role/DB, load datasets (sha256-tracked, idempotent), run learner SQL, question loading, validator.
- `server.py` — thin FastAPI routes. `ui/index.html` — the page.
- Datasets must be deterministic (no `random()`); a changed `schema.sql`/`seed.sql` is reloaded on the next Set up.

## Gotchas
- `docker-compose.yml` mounts `${TOOLBOX_PRACTICE_DIR:-../learn-sql/practice}` — keep the learn-sql repo next to toolbox or set the variable in `.env`.
- YAML turns bare `null`/`yes`/`no` into values — quote tags like `"null"`.
- `core/vault.py` seeds the Vault connection "Practice database (built-in)" (password `TOOLBOX_PRACTICE_PASSWORD`, default `practice-local-only`; not a secret worth protecting — it can only read practice data).
